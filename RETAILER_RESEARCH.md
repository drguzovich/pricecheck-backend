# Retailer Access Findings

On 18 August 2026, Pick n Pay’s public grocery site rendered a customer-facing product catalogue and stated that local availability and pricing depend on delivery details. The site presented a product search field and product cards with prices in a normal browser session. No official, documented product API credentials or approved server-to-server endpoint were identified during this review.

The PriceCheck backend therefore keeps Pick n Pay behind the `PNP_PRODUCT_LOOKUP_URL` configuration boundary. It can consume an operator-approved product-data provider without changing the public comparison contract. A public-catalogue fallback exists behind `PNP_PUBLIC_CATALOGUE_ENABLED=true`, but should not be enabled until a real barcode can be validated against the site in the deployment environment. The service does not attempt to bypass access controls or site protections.

On the same date, a normal browser session resolved the Woolworths Ouma Rusks URL and exposed the product-page title `Rusks: Ouma Buttermilk, 500g | Woolworths.co.za`. The browser extraction did not expose a reliable visible price in that session. The service must therefore continue to expose stale-cache status rather than claim that a browser title alone proves a current price.

Further direct-document validation established that the public Woolworths product URL returns an `application/ld+json` Product record with name `Rusks: Ouma Buttermilk, 500g`, SKU `6001069206154`, offer price `24.95`, currency `ZAR`, and a canonical product URL. This is now the backend's primary retrieval path, with browser automation retained only as a fallback.

Pick n Pay's public page identifies `https://www.pnp.co.za` as its OCC backend base URL and its client bundle references a `products/search` resource. However, direct unauthenticated candidate OCC paths returned the public HTML shell rather than JSON, and the normal public search flow did not yield a stable barcode result in the server automation environment. The public site also states that availability and local pricing depend on delivery details. No verified, compliant barcode-price endpoint was discovered, so the adapter remains correctly unavailable pending an approved provider or documented source.

Parse.bot documents a managed Pick n Pay product-search API with structured product name, price, stock, and image fields. Its public documentation confirms the endpoint requires an `X-API-Key`; an unauthenticated request returned `401 Missing X-API-Key`. The backend now supports this provider through `PARSE_API_KEY`, using known product metadata as the search query and retaining PriceCheck's original barcode identity. This path cannot be live-tested until a legitimate provider credential is configured.

Parse's published free tier provides 200 credits with no credit card and a 5-request-per-minute limit. Its signup form requires an account, agreement to provider terms, and hCaptcha. The account page is open in the browser, ready for the user to complete this external authorization step.

On 19 August 2026, the approved provider credential was configured in the deployed backend. The live endpoint verified an exact Pick n Pay result for barcode `6001069600754`: `Ouma Buttermilk Rusks Sliced 450g` at `R63.99`. Product metadata was resolved through Open Food Facts before the managed provider lookup, and the Pick n Pay response was accepted only because its public image URL contained the same EAN. The originally scanned barcode `6001069206154` remains correctly unavailable at Pick n Pay because the provider returned only different Ouma pack-size EANs; PriceCheck does not present those as an equivalent comparison.

The same managed provider was validated for Checkers on 19 August 2026. An exact EAN match for `6001069600754` returned `Ouma Butter Milk Sliced Rusks 450g` at `R62.99`, so Checkers now uses the price-enabled `products.checkers.co.za` managed endpoint with strict barcode matching. SPAR remains deliberately visible but unavailable: its public South African catalogue does not publish national prices because pricing is controlled at individual stores. A future SPAR integration requires a chosen store or geographic price provider.
